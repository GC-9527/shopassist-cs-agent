# 权限、回答格式与前后台拆分

这三个问题都是实际打开界面就能发现的：权限没真正校验、回答太模板化、C 端和后台混在一起。
下面记录改了什么、怎么验证的。

## 1. 身份可自报 → 改成令牌校验

### 原来的状态

`authorize_identity()` 本身是有的：会校验租户、以及"客户只能访问自己的资源"。
但 `SECURITY_ENABLED=false` 时，`get_current_principal()` 返回匿名主体，
所有校验直接放行——**请求体里的 `user_id` 就是身份**，谁都能自称 u001。

数据层是隔离的（订单查询按 `tenant_id + user_id` 过滤），但"你是谁"这件事没人验证。

### 改了什么

- 新增 `POST /api/v1/auth/demo-token`：只给白名单账号签发 JWT
  （`DEMO_LOGIN_USERS=u001:customer,u002:customer,u003:agent`）
- 默认开启鉴权：`SECURITY_ENABLED=true`
- 前端不再让用户手填身份，改成选择演示账号，令牌随请求携带；请求体里的 `user_id`
  由令牌主体回显

这是一个**演示用**的发令端点，不是认证系统：生产应该接企业 SSO，令牌只代表已认证的主体。
开放给任意账号等于没有认证，所以它默认关闭、且有白名单。

### 验证结果（实测）

| 场景 | 结果 |
| --- | --- |
| 无令牌调用 `/api/v1/chat` | 401 `authentication_required` |
| 白名单外账号申请令牌 | 403 `demo_account_not_allowed` |
| u002 的令牌 + 请求体写 `user_id=u001` | **403 `permission_denied`（Users may only access their own resources）** |
| u002 用自己的身份查 u001 的订单 | 200，但工具结果为空（数据层隔离） |
| u001 查自己的订单 | 200，返回真实物流 |
| 客户令牌访问坐席队列 | 403 `permission_denied` |

## 2. 回答太机械 → 约束格式 + 确定性清理

### 原来的状态

系统提示词只约束"内容不能编造"，没有任何格式要求，模型输出充斥着
✅❌🔹 和加粗小标题，像在念文档。

### 改了什么

- 提示词增加「回答格式」与「语气」两节：先给结论、不用 emoji、不用加粗分板块、
  步骤最多 3 条、引用标注 `[1]`、不向用户暴露内部字段
- 新增 `strip_decorations()`：提示词约束只是第一层，输出前再确定性地去掉
  emoji / 装饰符号，收敛多余空行。全被清掉时退回原文，不会输出空串

### 效果

同一问题的回答从

> ✅ **已发出（shipped）** 🚚 物流公司：顺丰速运 📦 运单号：SF1234567890

变成

> 订单 202606040001 已发货，由顺丰速运承运，运单号 SF1234567890 [1]。

## 3. C 端和后台混在一起 → 拆成两个界面

原来一个页面里左边聊天、右边是引用打分、工具回执、执行轨迹、人工队列——
这些都是内部信息，不该给 C 端用户看。

### 现在的结构

| 路径 | 面向 | 内容 |
| --- | --- | --- |
| `/` | 客户 | 只有对话、需要用户确认的操作、是否已转人工 |
| `/admin` | 坐席 / 运营 | 待处理会话（轮询 + 角标通知）、调试对话、证据轨 |

后台的"待处理会话"每 10 秒轮询一次，新到的会话高亮并挂角标；
生产环境应换成服务端推送。客户访问 `/admin` 或坐席接口都会被 403 拦住。

## 4. 顺带修掉的一个真问题：转人工从来没被触发

验证后台通知时发现：用户说"我要转人工客服"，系统回了一段兜底文案，队列里什么都没有。

三层原因：

1. **路由把它判成了知识问题**（"转人工"是业务域但不是查询请求），
   于是走 RAG，模型在知识库里看到"什么情况必须转人工"就照着回答
2. **模型没有真的调用 `transfer_to_human`**，却说了"已为您转接"，被输出校验拦下
3. **转人工工具被设成需要二次确认**，用户主动发起的低风险动作还要再点一次

修复：

- 意图分类器区分"我要转人工"和"什么情况必须转人工"：前者是**显式动作请求**
  （`explicit_handoff_request`）
- 编排层对显式转人工**直接执行工具**，不交给模型自由裁量
- `transfer_to_human` 改为低风险、无需二次确认（可逆动作）
- 队列返回 `reason` / `priority`，前端原来只读不存在的 `summary` 字段，已修正

验证：C 端说"我要转人工客服" → 工单创建 → 坐席队列出现 1 条，
带原因、优先级、状态，客户端访问队列返回 403。

## 5. 界面视觉：改成电商客服中心的样子

第一版的 C 端虽然拆开了，但视觉上还是内部工具的样子：白底、细线、没有明确的聊天形态。
现在按主流电商客服中心的观感重做：

- **顶栏**：深色 `#1b2430`，白色品牌与导航，橙色高亮当前入口
- **聊天卡片**：白色圆角卡片 + 细边框 + 极轻阴影，占满可视高度
- **气泡**：助手在左（浅灰 `#f0f2f2`，右下角切角）、用户在右（浅蓝 `#dceefb`，左下角切角），
  带 26px 头像圆点
- **输入区**：圆角输入框 + 橙色圆形发送按钮，聚焦时青色描边
- **订单入口**：白卡片列出商品、金额、订单号、物流，操作用青色文字胶囊按钮
- **在线状态**：绿色圆点 + "在线 · 通常立即回复"
- **打字指示**：三点呼吸动画

配色沿用电商的语义习惯（橙色=主操作、青色=链接、绿色=成功/在线），
但这些是通用设计语言，没有使用任何平台的商标或素材。

## 6. 对照主流云客服聊天组件补的聊天细节

我们对照了业界云客服聊天组件常见的功能清单：消息回执、富文本、交互式按钮、附件、会话时长、持久会话等。
没有照搬任何一家的实现，只按能力清单补齐自己缺的部分。

按这份清单，我们补了四项真正缺的：

- **系统提示行**：对话开始时显示"已接入在线客服"，转人工后变"已为您转接人工客服"
- **消息时间戳**：每条气泡右下角显示 HH:MM
- **输入长度上限**：1000 字，超出时显示计数
- **无障碍播报**：消息区加 `aria-live="polite"`，新消息会被读屏软件读出
- 头部按钮从"新会话"改成"结束会话"，与聊天语境的惯例一致

**没有做的**：消息已读回执。它需要真实的消息投递状态，没有投递链路时做出来就是假的——
宁可不做。附件上传已补（见第 9 节），落的是真实文件而不是占位图。

**关于界面素材**：没有扒任何线上产品的 DOM 或样式。第三方平台的前端样式属于其版权内容，
直接复制既有风险，也会让"这是我自己做的项目"这句话站不住。
我们按通用交互模式自己实现，界面与品牌统一为 ShopAssist。

## 7. 工作台布局（按产品设计稿重做）

C 端改成左右两栏的工作台式布局，参照的是产品侧提供的设计稿：

- **二级导航**（`#232F3E`）：页面标题 + 常用入口 + 引擎在线状态
- **左栏**：欢迎卡（转人工 / 退换货政策）、我的订单（可点选，选中态高亮）、快捷服务四宫格
- **右栏聊天卡**：头部（头像 / 助手名 / AI 徽标 / 在线状态 / 转人工 / 结束会话）、
  关联订单条（显示当前选中的单号，可切换）、消息流、快捷胶囊、输入区（黄色发送按钮）

气泡按设计稿改成：用户侧青色底白字靠右，助手侧白底描边靠左，
两者都在气泡上方显示"发送者 · 时间"，并带圆形头像。

**品牌边界**：设计稿里的第三方平台商标字样和 Logo 没有照搬，
界面品牌统一为 ShopAssist；配色（`#131921` / `#232F3E` / `#FF9900` / `#FFD814` / `#007185`）
属于通用电商视觉语言，界面结构按稿子实现。

## 8. 会话恢复（persistent chat）

业界云客服产品普遍提供 persistent chat：客户重新进入时，把上一次会话的记录重新接上，
不用重复描述问题。我们按同样的语义实现，但用自己的存储：

- `conversations` 表新增 `thread_id`：恢复时要接回原来的 LangGraph 线程，否则多轮上下文会断
- `GET /api/v1/conversations/latest`：返回最近一条会话，超过恢复窗口（默认 24 小时）或已结束则返回 null
- `POST /api/v1/conversations/{id}/close`：结束会话，之后不再自动恢复
- 前端打开页面即拉取最近会话；恢复成功时时间横幅显示"已恢复上次会话 · 上次活动 HH:MM"
- "结束对话"与"重置会话"都会真正关闭会话，而不是只清空本地状态

### 一个语义上的坑

第一版把"排除已结束"下推到查询里，结果是：**结束最新会话后，会翻出更早的一条旧会话顶上来**。
现在改成只看最近一条——它结束了就从头开始，不会把几周前的对话重新拉出来。

### 又一个 updated_at 的坑

`close_conversation` 里改 `status` 后 flush，`updated_at` 带 `onupdate=func.now()` 仍是未加载状态，
响应序列化时触发同步懒加载，接口直接 500。和之前 pending_actions 那次是同一类问题，
修复方式是 flush 后显式 `refresh(conversation, ["updated_at"])`。

## 9. 附件上传（售后凭证图片）

参考同一份清单里的 attachments，补了"用户拍图说明破损"这条真实链路：

- `attachments` 表（`migrations/0011`）：记录归属租户/用户、文件名、类型、大小、落盘路径
- `POST /api/v1/uploads`：multipart 上传，只收 JPG / PNG / WebP，超过 5MB 直接 413
- `GET /api/v1/uploads/{id}`：按归属校验——本人、坐席/运营、平台管理员可读，其他人 403
- 聊天请求可带 `attachments`，落进用户消息的 `metadata.user.attachments`，刷新后仍能还原

### 三个容易漏掉的点

1. **图片不能直接放进 `<img src>`**：下载接口要 Bearer 令牌，而 `<img>` 不会带自定义头。
   前端先用 `fetch` 拉成 blob，再 `URL.createObjectURL` 给 `<img>`，并按附件 ID 缓存，
   同一条消息重复渲染不会重复下载。
2. **聊天接口不能信任客户端给的附件 ID**：不校验就能把别人的凭证图挂到自己消息上。
   `/chat` 与 `/chat/stream` 在进入 Agent 前统一按 `tenant_id + user_id` 查一遍，不匹配返回 403。
3. **模型没有视觉能力**：不能假装"看见了图片"。只把文件名告诉模型，由话术请用户描述或确认诉求，
   不臆测图片内容。

### 顺手修掉的一个脏输出

实测时模型给出 `可申请换货[4]。`——`[4]` 是检索片段编号，只对调试有用。
`strip_decorations` 增加了纯数字角标清理（`[4]`、`[1,2]`、`【3】`），
方括号里的正常文字（如 `[订单号]`）不受影响。

验证：177 个测试通过；接口实测上传 200、下载 200、他人读取 403、匿名 401、坐席 200、
跨用户挂附件聊天 403、纯文本上传 400；浏览器实测选图→预览胶囊→发送→气泡缩略图→刷新后还原。

## 10. 结束会话后的满意度评价（CSAT）

对话结束后让客户给这次服务打分，是客服系统的常规闭环。实现分三块：

- `csat_ratings` 表（`migrations/0012`）：租户 / 用户 / 会话、1-5 星、选填评论、预置标签
- `POST /api/v1/conversations/{id}/csat`：只有会话本人、且会话已结束才接受评价
- `GET /api/v1/csat/summary`：坐席/运营/管理员才能看全租户汇总，客户调会 403

### 语义上的几个决定

1. **一条会话一条评价，重复提交覆盖**。否则客户连点两次，后台样本就被重复计数。
2. **必须先结束会话**。评价针对的是"这次服务"，会话还开着就提交没有意义；接口用 409
   明确拒绝，前端也只在关闭成功后才显示评价卡片。
3. **标签固定枚举、评论自由文本**。标签用于聚合，评论只做展示；未知标签直接丢弃，
   不让前端随便塞值污染统计。
4. **后台只读**。管理员可以看汇总和评论，但没有修改入口——改写客户评分会让这个指标失去意义。

### 验收时发现的一个既有 bug：时区

做后台列表时发现，恢复会话横幅显示"上次活动 14:48"，而本地时间是 22:48。
原因是 MySQL `DATETIME` 不存时区，应用写入 UTC，接口把 naive 值直接 `isoformat()`，
浏览器按本地时间解析，东八区就差了 8 小时。

修复：新增 `core/time_utils.as_utc()`，数据库读出的时间在序列化前补上 UTC 标记；
会话横幅、消息时间、评价时间统一走它。客户侧的消息时间本来就是本地 `Date.now()`，
所以这个问题只在"刷新后恢复"的路径上暴露。

验证：184 个测试通过（新增 7 个 CSAT 单测），前端构建通过；接口实测
未结束评价 409、评价他人会话 404、结束后评价 200、重复提交覆盖、客户读汇总 403；
浏览器实测 结束对话 -> 评价卡片 -> 5 星 + 标签 + 评论提交 -> 感谢态 -> 后台看板出现该条数据。

## 11. 会话状态机（Bot / 排队 / 人工 / 待确认 / 结束）

转人工的状态转移在后端早就有了（`waiting_assignment → assigned → in_service →
resolution_submitted → resolved`），但 C 端只在"发出去的那一句话"里知道状态，
坐席什么时候接入、前面还有几个人、结论有没有出来，客户都看不到。
这一节补的是**客户侧可见的状态机**。

- `GET /api/v1/conversations/{id}/session`：返回 `status + service_mode + handoff`
  （含队列位置、坐席 ID、处理摘要），归属校验与其它会话接口一致
- 队列位置用后台队列同一套排序（优先级 → 请求时间）计算，只有 `waiting_assignment` 才有位置
- 前端每 4 秒轮询一次；进入排队/人工/待确认后，同时轮询消息，把人工通道的回复补进对话

界面上的对应关系：

| service_mode | 客户看到 |
| --- | --- |
| `bot` | 无状态条，正常和机器人对话 |
| `waiting_human` | "正在为您转接人工客服 · 前面还有 N 位" |
| `human` | "人工坐席 u003 已接入"，消息署名改为人工坐席 |
| `resolution_review` | "坐席已提交处理结果，请确认" |
| `closed` | 输入框禁用、占位改为"会话已结束"，并弹出满意度卡片 |

### 几个容易漏的边角

1. **人工通道的消息不走 SSE**，不轮询就永远收不到；轮询只补 `metadata.channel == "human_support"`
   的助手消息，避免把客户自己发的消息（本地先渲染过）重复插入。
2. **客户排队时点"结束对话"**：如果只改会话状态，后台队列会留下一个永远不会被分配的
   转人工任务。`close_conversation` 现在会一并把活动 handoff 置为 `cancelled`。
3. **人工消息不能标成"智能客服 Agent"**：消息带 `channel`/`agent_id`，气泡头像和署名都换掉。
4. **`updated_at` 的又一次坑**：`onupdate=func.now()` 的列在 UPDATE + flush 后是过期状态，
   序列化 handoff 响应时触发同步懒加载，接口 500（`MissingGreenlet`）。所有状态转移现在
   显式写 `updated_at`，不再依赖数据库回填。

演示账号新增 `u004:operator`，用于确认坐席提交的处理结果（agent 角色没有确认权限），
把"排队 → 接入 → 回复 → 提交结果 → 运营确认 → 回到 Bot / 结束"跑完整。

验证：187 个测试通过（新增 3 个状态机单测），前端构建通过；接口实测完整状态转移、
人工接管期间客户消息只入库不触发 Bot、排队中结束会话会取消转人工；浏览器实测
状态条随坐席接入/提交结果实时变化、人工消息自动出现、坐席结束会话后自动弹出评价卡片。

## 12. 后台人工处理面板

状态机做完后，React 后台的"待处理会话"依然只能看不能操作，坐席真正干活还得去 FastAPI
自带的 `/ops` HTML 页面。这一节把接入、回复、提交结果、确认结果搬进 `/admin`：

- 队列行可点击，选中后在主区域打开处理面板
- **接入**：`waiting_assignment` 状态显示"接入会话"，接入后客户侧状态条变成"人工坐席已接入"
- **回复**：`assigned / in_service` 状态下以坐席身份发送消息，消息直接进入会话历史
- **提交处理结果**：选择处理方式（换货 / 退款 / 已告知 / 升级 / 其他）、填写客户可见摘要，
  并选择处理完后"转回机器人"还是"结束会话"
- **确认**：只有运营/管理员角色能看到；按钮文案跟随提交时选的去向
  （"确认并恢复 Bot" / "确认并结束会话"）

### 一个被面板暴露出来的旧问题

处理面板一上线就发现队列里混着"已解决"的历史任务。原因是 `/human-support/queue`
不传 `status` 时会把该租户所有转人工记录都返回来，后台看起来像还有一堆活。
现在 `list_queue` 在不指定状态时默认只取活动状态（`waiting_assignment / assigned /
in_service / resolution_submitted`），历史记录不再占队列。

另外面板里的消息时间也统一走本地时间格式化，避免再出现"UTC 当本地"的 8 小时偏差。

## 13. C 端不展示内部执行信息

截图里暴露过两个问题：确认完成后，客户侧出现了"原 LangGraph 线程已恢复并执行完成"
和"工具回执：create_refund_case 成功"；确认提示本身还是英文。

根因有三处：

1. `useChatSession.decide` 对所有角色都把 `tool_results` 拼成"工具回执"追加进气泡；
2. 确认接口的兜底文案是内部描述（线程恢复、执行完成）；
3. 确认提示由工具层生成英文，没有跟随租户语言。

修复：

- `useChatSession` 增加 `showInternals` 参数：只有 `/admin` 打开，C 端不拼工具回执；
- 确认完成后不再跑模型，直接用工具回执拼一句客户能看懂的结果
  （如"退款申请已提交，工单号 …。处理结果会在这里同步。"），避免再带回内部文本；
- 确认提示按租户语言生成，中文租户输出中文；
- 等待确认时 C 端只显示确认卡片，不再把同一段提示重复成气泡；恢复历史时
  按 `metadata.type == "confirmation_required"` 过滤掉确认提示，后台仍保留。

验证：中文订单取消 → 中文确认提示 → 批准后只出现一条"退款申请已提交"，
刷新后历史里没有确认提示气泡、没有工具回执；后台仍能看到工具与回执。
