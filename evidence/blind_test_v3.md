# 第四套盲测：验证意图分类 + 关键词通道

## 为什么还要一套

前三套数据（调参集、盲测 v1、盲测 v2）都已经被用来定位问题。
任何一套被读过失败样本之后，它就不再是盲测——它变成了调参数据。
要判断这一轮机制改造到底有没有真实提升，只能换一套没参与过诊断的新种子。

所以另建了 40 条种子（`eval/seeds_blind_v3.json`），与前三套问题零重叠，
覆盖的是之前没问过的条款事实，由 `tests/test_eval_set.py` 守住。

## 设计

| 项 | 值 |
| --- | --- |
| 独立语义种子 | 40 |
| 每条表达变体 | 10 |
| 合计 | 400 条 |
| 切分 | 开发 230 / 测试 170，按种子分组 |
| 类别 | 政策 7、排障 7、售后 9、风控 6、企业 SLA 4、实时工具 3、超纲 2、对抗 2 |

## 结果

| 指标 | 值 |
| --- | ---: |
| 检索 Hit@5 | **0.979** |
| 检索 MRR | **0.923** |
| 路由准确率 | **0.997** |
| 只看原句 Hit@5 | 1.000 |
| 开发集 / 测试集 Hit@5 | 0.990 / 0.964 |

按类别：排障 1.000、企业 SLA 1.000、政策 0.986、售后 0.967、风控 0.950。
路由：工具类 0.967，其余类别全部 1.000。

失败只有 7 条，集中在**改写把关键词换掉**的情况：
"售后方案执行前要展示哪些信息"被改写成"应当向顾客呈现哪些内容"（用户→顾客、展示→呈现），
"签收信息和陈述矛盾"被改写成"签收记录跟客户讲的不是一回事"。
这些改写丢掉了与文档原句重叠的词，稠密向量也没能把它们拉回来。

## 怎么读这个数字

| 数据集 | 状态 | Hit@5 | MRR | 路由 |
| --- | --- | ---: | ---: | ---: |
| 调参集 600 | 已用于诊断 | 0.994 | 0.926 | 0.995 |
| 盲测 v1 450 | 已用于诊断 | 0.987 | 0.920 | 1.000 |
| 盲测 v2 400 | 已用于诊断 | 0.956 | 0.889 | 0.995 |
| **盲测 v3 400** | **干净** | **0.979** | **0.923** | **0.997** |

**结论要克制：这轮机制改造没有带来决定性的检索提升。**

- 改造前，盲测 v1 第一次跑出来的干净数字是 0.984 / 0.909 / 0.988
- 改造后，一套全新种子上是 0.979 / 0.923 / 0.997
- Hit@5 差 0.5 个百分点，但这是**两套不同的种子集**，集合之间的难度波动就大于这个差值；
  不能把它当成"提升"或"退步"的证据

真正能确认的改进在另外两处：

1. **路由从 0.988 到 0.997**，且在干净集上工具类只剩 1 条错误——特征分类确实比关键词规则稳
2. **可解释性**：每条路由决策现在带 `signals` 和置信度，能回答"为什么走了这条路"，
   关键词规则时代只能回答"因为命中了哪个词"

检索侧的瓶颈不在融合策略，而在**表达与文档措辞的重叠度**。
继续调权重和阈值收益有限，真正的下一步是查改写（query expansion）或者换多语言更强的向量模型。

## 口径

这一套在跑之前没有读过任何失败样本，上面的数字是它第一次跑出来的结果。
如果继续根据它调规则，它也会退化成调参集——下一轮要说"提升"，仍然需要第五套。
